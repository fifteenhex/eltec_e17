=== 2026-09-22: Bug B FIXED (LANCE DMA-into-freed-memory at u-boot->kernel handoff) ===

free()d priv->rxbuf without waiting for the Am7990 (bus master) to quiesce. In-flight rx

RAM corruption -> intermittent silent hard-hang right after kernel TFTP/CRC, before console

eth_halt() DOES reach lance_stop before bootelf (net_loop line 783 calls it unconditionally),
so no elf.c change needed -- confirms the user's chosen driver-side fix over re-adding the
reverted bootelf_exec CSR0=STOP poke (b8e0be2d206 / revert 3b1a2fa8cb7).
FIX: poll CSR0 until RXON|TXON clear before freeing, bounded 100ms (can't hang boot itself);
fixed free order. Committed u-boot e17-fixes 855e79ea391, deployed (u-boot.e17boot crc 04f8b940).
VALIDATION (real board, clean power-cycle baseline): 6/6 clean boots after fix, 0 Bug B, 0 Bug A.

=== 2026-09-22: Bug A root-caused (the remaining boot instability) ===
Finer-milestone soak (20 boots, stopped at 10): 7 clean, 3 failures (boots 2,7,9). ALL three
failures reported prev-boot milestone 0x27 (E17_EARLY_SERIAL: serial console already up) and are
RCU-stall panics (panic_on_rcu_stall -> reboot via watchdog; self-heals). Two captured signatures,
same root:
  boot 2: CPU0 stuck in on_each_cpu(ipi_flush_tlb_all) <- __ioremap in e17drm probe; RCU stall
          detected from CPU0's tick. CPU1 not acking the cross-CPU TLB-flush IPI.
  boot 7: "Possible timer handling issue on cpu=1, timer-softirq=24"; rcu_sched kthread starved
          on cpu=1 (CPU1 running kdevtmpfs, R). CPU1's scheduler tick stopped preempting it.
UNIFYING ROOT CAUSE (Bug A): in the early-device-init window right after AP bring-up, CPU1's
cross-CPU coordination is unreliable -- its VIC-clock level-4 tick and/or its servicing of the
mailbox/CALL_FUNC IPI intermittently stall. Result: either CPU0 hangs on a synchronous cross-CPU
TLB flush (driver ioremaps do flush_tlb_all = on_each_cpu), or CPU1 starves rcu_sched -> RCU stall
-> panic=10 reboot. The IPI backstop (per-tick drain) and e17_smp_reg_lock did not prevent it
(the backstop itself relies on CPU1's tick, which is the thing that dies).
No AP VIC-clock storm/runaway DISABLE message preceded boots 7/9, so the storm self-protection is
NOT the trigger here; the level-4 tick delivery/servicing itself stalls.
STATUS: Bug B (dangerous brick) FIXED+validated. Bug A (this) is recoverable (self-heals via
panic=10 reboot -> ~10-30% of boots need one retry), now precisely root-caused with stack traces.
The fix is a deep m68k SMP tick/IPI-delivery investigation in the delicate VIC-clock AP-tick /
CPU2CON path -- flagging for a design decision rather than a blind change under board-hang risk.

=== 2026-09-22: level-7 (NMI) TLB IPI rework DONE; splits Bug A into two mechanisms ===
Implemented CONFIG_E17_SMP_NMI_TLB (default y in e17 defconfig): the boot CPU delivers its
cross-CPU flush_tlb_* to the secondary as a level-7 (non-maskable) mailbox IPI so it pierces
the secondary's spin_lock_irqsave IPL-7 mask. Lock-free NMI handler (raw mailbox ack + local
pflusha), plain req/ack handshake (single writer each, sender synchronous IRQs-off), bounded
spin -> falls back to on_each_cpu. Only boot-CPU->secondary is rerouted. Committed e17-clean
ac6abd9213b5.
VALIDATION (hardware): the NMI path is real and reliable -- clean boots report
"E17 SMP: NMI-TLB usage: N acked, 0 timed-out->fallback" (7 acked, 3 acked seen; ZERO
timeouts). So A1 -- the CPU0-stuck-in-on_each_cpu(ipi_flush_tlb_all) deadlock (the boot-2
signature) -- is addressed: the secondary now services the flush even mid-spinlock.
BUT Bug A is NOT one bug. A soak still hit RCU-stall reboots with a DIFFERENT signature:
  A2 = CPU1 tick death: CPU0 IDLE (default_idle_call), CPU1 running kdevtmpfs (R), rcu_sched
       starved on cpu=1, "Possible timer handling issue on cpu=1 timer-softirq=NN" (tick fired
       ~76 times then STOPPED). No VIC-clock storm/runaway DISABLE message -> not the self-
       protect. This is NOT a TLB-flush deadlock (CPU0 isn't flushing), so the NMI-TLB fix
       does not and cannot address it. A2 pre-dates the NMI fix (finer-milestone soak boot 7).
NET: IPI/NMI rework finished and confirmed working; it resolves A1 (TLB-flush-deadlock cause of
the early RCU stall). A2 (the AP/VIC-clock level-4 tick intermittently dying early in boot) is a
separate, still-open mechanism -- the next target. Soak rate was unmeasurable cleanly (telnet-
auth-race + netboot-driving TIMEOUTs muddied it). Board self-heals from both (panic=10 reboot).

=== 2026-09-22: Bug A2 FIXED and validated (AP tick run with IRQs masked) ===
Built an NMI-backtrace facility (CPU0 NMIs CPU1 when its tick heartbeat freezes; the level-7
NMI pierces the IPL-7 mask and records CPU1's PC/stack/regs). It caught A2 red-handed:
  CPU1 stuck: do_raw_spin_lock <- raw_spin_rq_lock <- sched_ttwu_pending  (inner, IPL7)
              <- handle_IPI(CALL_FUNC) <- e17_ipi_isr                     (the level-6 IPI)
  outer holder (same CPU1): sched_tick -> task_tick_fair -> update_load_avg
  CPU0 idle; CPU0's view of the rq lock = 0x03de03dc / 0x073f073d = HELD (real deadlock, not a
  stale-cache coherency miss; that hypothesis was tested and rejected via the CPU0-side read).
ROOT CAUSE: the AP VIC-clock tick is a level-4 autovector, so e17_ap_tick() runs at IPL4, which
masks only <=4 and leaves the level-6 mailbox IPI able to NEST. sched_tick() takes the rq lock
with rq_lock() (a plain raw_spin_lock that assumes the timer IRQ already runs IRQs-off, true on
every other arch). On m68k it doesn't: the level-6 IPI nests into the rq-lock-held tick and
sched_ttwu_pending() re-enters the same ticket rq lock -> self-deadlock -> CPU1 tick dies ->
rcu_sched starves -> panic_on_rcu_stall reboots. (CPU0's tick is level 6 == the IPI level, so it
is already nesting-safe; only the AP tick was affected. First m68k SMP board, so first to hit it.)
FIX: run the AP tick body (legacy_timer_tick + the IPI-backstop drain) under local_irq_save()
(IPL7), restoring the IRQs-off-timer-handler invariant the scheduler relies on. The level-7 NMI
TLB path is unaffected (non-maskable, lock-free). Committed linux e17-clean 6505d5862c7e.
Tried-and-rejected along the way: removing the per-tick IPI backstop (A2 persisted AND early
lost-edge hangs got worse -> backstop restored).
VALIDATION (real board): 15/15 clean boots, A2=0, other=0. Zero tick-dead captures since the fix
(the diagnostic stays in, harmless). Before: A2 hit ~1 in 3-7 boots.
Bug A now fully resolved: A1 (TLB-flush deadlock) via level-7 NMI TLB; A2 (tick-vs-IPI rq-lock
re-entrancy) via IPL7 AP tick.

=== 2026-09-22: Bug D root cause via VIC dump + ICR RMC fix (IN VALIDATION) ===
Added VIC068A full register dump (irqchip late_initcall) + read the datasheet at
/workspace/files/VIC068A_register_map.md. Live config decoded:
  TTR $A3=0x44 : local-bus timeout ENABLED 16ms (but BESR $BB=0x00 -> never fired,
                 so the hang is NOT a plain no-DTACK cycle).
  ICR $AF=0xf0 : SCON=0 (VIC is VME system controller); bit4=1 deadlock->HALT*+LBERR*
                 +DEDLK*; bits7-5=1 = RMC control (bit5 = "request VMEbus whenever
                 RMC* asserted, independent of MWB*").
  ARCR $B3=0x60: fairness disabled, round-robin, VME req BR3.  RCR $D3=0x00: ROR.
ROOT CAUSE (hypothesis, high confidence): the 68040 asserts RMC* on every locked
CAS/TAS (every spinlock/atomic). ICR bit5=1 => VIC fires a VMEbus arbitration
request on EVERY SMP spinlock, though DRAM is local. SMP-startup spinlock storm
floods VME arbitration; a deadlock asserts HALT* (bit4) to BOTH CPUs -> whole-bus
hang, both frozen at random PCs, watchdog reset (the 16ms local timeout doesn't
catch a HALT*). Matches: e17drm-on unreliable, blit/console/getty tweaks don't fix.
FIX (committed linux e17-clean ea342cd, deployed kernel crc ab3e3987): at irqchip
probe (before SMP bring-up) read-modify-write ICR &= ~0xe0 (clear RMC->VMEbus bits
7-5). ICR write is NOT SYSRESET-risky (only SRR $E3<-$F0 is). Local CAS no longer
touches the VMEbus. VME-side RMC/atomicity deferred (we don't use VME yet).
VALIDATION IN PROGRESS: soak logs/real-board/boots/bugD-icrfix-*.out. Metric =
telnetd listening (full userspace). Guardrail: cross-CPU atomicity self-test must
still pass (CAS bus-atomic). Boot 1 still reset (0x60) -- need the rate over more
boots; a clean boot's VIC re-dump (late_initcall) will confirm ICR=0x10.
IF THIS DOESN'T WORK: next levers = also clear ICR bit4 (deadlock->HALT* : set to
DEDLK-only so a deadlock doesn't halt the CPUs); or reduce TTR local timeout; or
the SS0CR0/arbitration. All non-SYSRESET (avoid SRR $E3).
