ELTEC EUROCOM-17 - hardware session 2026-09-21 (UART + watchdog + first lockup post-mortem)
==========================================================================================

Access: RMON -> our u-boot (netbooted as e17/u-boot.e17boot) -> netboot Linux.
Console over serial2mqtt (m68k/e17/serial); files over file2mqtt (m68k/e17/files).


1. U-BOOT UART - FIXED AND VERIFIED
-----------------------------------
Four distinct bugs, all found on hardware:

 a. A bit-7 "request pending" flag was invented for TIR/RIR. It does not exist:
    the working kernel driver defines only TIR_TACT (0x40, bit 6 = service
    active) and never reads bit 7. The ack loop therefore never issued the
    software IACK, every putc dropped its character, and the console went
    silent. Fixed by following the kernel driver: one shared priority level for
    all three services, IACK at the single 0x7b window, dispatch on the returned
    vector type rather than the one wanted.

 b. TX and RX were given different PILR levels. With a character waiting the
    chip favours receive, so an IACK at the transmit level matched no PILR, went
    un-DTACKed, and stalled the bus (no bus-error timeout on this board). This
    was the original "type a word at the prompt and the board dies".

 c. A 1.665 s unpetted window across relocation into initr_dm, against the
    1.6 s watchdog period -> a HEALTHY board reset 65 ms short of "Now running
    in RAM". Fixed with early WATCHDOG_RESET() in board_r and direct pets in the
    CD2401 poll loops.

 d. lz4 -9 defaults to 4 MB blocks; u-boot's lz4 wrapper pets once per frame
    block, so the 3.9 MB kernel was ONE 18 s unpetted decompress. Fixed in
    packaging with -B4 (64 KB blocks); ~6% larger.

Verified on hardware: `version` (7 chars, the command that hung the old build),
a 60-char paste through the 16-byte FIFO, and five rapid commands incl. bdinfo -
all echoed and executed cleanly.


2. WATCHDOG SELF-RECOVERY - WORKING
-----------------------------------
u-boot now arms the board watchdog ($FEC5.0000) in cpu_init_f, before the serial
probe (the fragile part), and pets from schedule() + board_r. RMON prints
"### Watchdog Reset" and reloads automatically. Observed the board recover from a
Linux hang to a u-boot prompt unattended, repeatedly. The hardware cannot be
disarmed once armed, so the kernel now MUST pet it too (see 3).


3. LINUX BOOT - was dying 1.6 s after entry with zero output
------------------------------------------------------------
Root cause: u-boot arms a watchdog the kernel never fed; e17_wdt probes far too
late. Fixed by petting early: head.S at entry (moveb #0,0xfec50000 as the 2nd
instruction), config_eltec_e17(), the 100 Hz tick, and around console writes.
After that e17_wdt takes over (hw 1600 ms, hard-IRQ pet every 400 ms). Linux now
boots to userspace: SMP up, both CPUs online, /init runs.


4. LINUX UART (goal 2) - root-caused, fixed, NOT yet verified on hw
------------------------------------------------------------------
 a. poll=1 and txirq=1 both default on, and were inconsistent: poll mode gives
    RX a private IACK window (RPILR=CD2401_RX_IPL) and the rx timer acks there,
    but the interrupt-mode putchar reprograms ALL THREE PILRs to the shared
    0xfb. The first printk after startup thus clobbers RPILR, every later rx ack
    matches no PILR, and receive dies. Fixed: e17_cd2401_tx_one() honours poll.
 b. telnetd spawns /sbin/getty per session, but getty was never in the
    initramfs -> every telnet connection accepted then instantly died with no
    shell. With serial RX also broken (a) that left NO way into the board.
    Fixed: getty added at /sbin/getty; init respawns telnetd.


5. LOCKUP POST-MORTEM - overturns the documented theory
-------------------------------------------------------
The NVRAM breadcrumb dump was gated on PA7==0, but RMON's own watchdog petting
clears the PA7 front-panel indication before Linux looks, so on a netbooted
board it reads 1 and the entire post-mortem was silently discarded. Ungated it
(the breadcrumb has its own validity magic; PA7 still decides WDIOF_CARDRESET).

First real dump, from a genuine hang after ~128 s of uptime:

  CPU0 hb=234, CPU1 hb=166 (snap 101); CPU1 ticked 65 more
    -> CPU0-only stall (IRQs-off/level-6), bus alive
    last region 0x00 (none/idle)
  CPU0 last-tick PC 0x0000a9d0 (arch_cpu_idle+0x4/0x6); irq_err_count=0, badvec=0
  CPU1 last-tick PC 0x0000a9d0 (arch_cpu_idle+0x4/0x6)

This is NOT a whole-bus hang (README section "known hang problem" assumes one):
CPU1 ticked 65 times after CPU0 died, so the bus was alive throughout. CPU0
alone went into stop #0x2000 (arch_cpu_idle) and was never resumed - and its own
tick is level-7 (non-maskable) and auto-clears on IACK, so a stopped tick means
CPU0 itself is wedged in the stop state, not a maskable-interrupt problem. The
CD2401 IACK path is NOT implicated (region=none, irq_err_count=0, no bad vector).

Secondary observation (running degraded build): rcu_sched kthread starved,
"Possible timer handling issue on cpu=1", telnetd state:R running - i.e. CPU1
softirq/timer starvation. Consistent with the getty bug churning telnetd; the
getty + telnetd-respawn fixes should clear it. Both symptoms are interrupt/timer
DELIVERY problems, not bus problems.

Candidate fix under test: e17_idle boot arg (halt|spin). Code default stays
halt; the E17 netboot bootargs opt into e17_idle=spin, which uses the existing
non-halting poll-baseline idle (drains IPIs, bounded register-only spin, then
returns to the idle loop). It cannot get permanently stuck, so if the hang
disappears the mechanism is confirmed as stop-instruction wakeup loss; if it
persists it is VIC/bus routing. Either way the next boot is decisive.

Also added: panic_on_rcu_stall=1 panic=10 in bootargs, so a half-working board
(timers limping, watchdog still fed, unreachable) reboots instead of stranding.

==========================================================================================
RESOLUTION (same session, after board reset by the user)
==========================================================================================

With the board reset available again, all fixes were verified on hardware:

GOAL 1 (u-boot UART): stable and verified (version, 60-char paste, rapid cmds).

GOAL 2 (Linux UART):
 - Serial console OUTPUT: rock-solid (always was).
 - Telnet input path: FIXED and verified. Root cause of the earlier silent
   telnet was getty: telnetd execs /sbin/getty per session, but getty was not
   in the initramfs AND getty's mkdir /run/seat-* failed (no /run). Added getty
   at /sbin/getty and created /run,/tmp,/etc. Telnet now gives a full shell
   (uname -a etc.), and init respawns telnetd if it dies.
 - Serial console INPUT: the poll/txirq (PILR-window) fix made single commands
   work, but under sustained/concurrent load the CD2401 receive path drives CPU0
   into a double-fault halt (CPU0-only stall, bus alive, level-7 tick stops;
   region none; independent of HW_IPI y/n). This is the documented board-level
   CD2401 hazard. Contained by defaulting the console to OUTPUT-ONLY
   (serial_e17_cd2401.console_rx=0): the concurrent serial+telnet stress that
   reliably wedged every prior build now PASSES (board steady at 3-5 ms ping,
   no reset). console_rx=1 re-enables input for light use. Robust RX under load
   remains open; telnet is the input path.

GOAL 3 (lockups / watchdog reboots):
 - Spontaneous idle stall FIXED by e17_idle=spin: old build hung at ~128 s idle;
   fixed build ran 9+ min under load, both ticks ~100 Hz, ERR=0. Confirmed the
   breadcrumb signature is CPU0-only (bus alive), not whole-bus.
 - Watchdog self-recovery verified repeatedly (board returns to u-boot prompt
   unattended). panic_on_rcu_stall=1 set from init (boot-arg form is rejected)
   + panic=10 covers the half-wedged "pings but unreachable" state.
 - Residual: a whole-bus cross-call hang during reboot (CPU0 in
   smp_call_function_many_cond; CPU2CON doorbell write to the other CPU).

Convenience: u-boot default bootfile now e17/vmlinux.e17.stripped.lz4, so a bare
"run netboot" boots the kernel under test (env has no writable store yet; the
user offered spare NVRAM for env - deferred pending a safe NVRAM-size probe,
only ~240 B look free at 0x610-0x6ff on the 2 KB part).

ADDENDUM - smolutils master migration + working reboot (same session)
==========================================================================================

USERSPACE now builds from smolutils master via its own manifest:
 - build-rootfs.sh builds smolutils (Makefile.m68kmmu CPU=68040 NOPIE=1) and
   lays the rootfs out with tarwak + rootfs.tarwak.json (bsdtar -> newc cpio):
   /lib/smol multicall binaries, /bin+/sbin symlink farm, /init -> /sbin/init,
   and file capabilities.  Device nodes + init-smptest appended via
   gen_init_cpio.  Needs bsdtar and tarwak (meson).
 - Proper root: getty drops the login to uid 1024; `su` regains root from a
   cap_setuid file capability that smolutils' startup applies at boot.  That
   needs CONFIG_TMPFS_XATTR (added) so the initramfs rootfs can hold the
   security.capability xattr - without it startup logged "Failed to label
   /bin/su: 95" and su could not work.
 - Auth: telnet login and su each print a random code on the securetty (the
   serial console, smolinit.securetty=/dev/ttyS0) and ask for it back.  The
   serial console is output-only (console_rx=0), so the code appears on
   serial2mqtt; scripts/e17-telnet.py reads it from build/console.log and
   answers.  VERIFIED: telnet -> uid 1024 -> su -> Uid: 0 0 0 0 (root).
 - bootargs: "... e17_idle=spin panic=10 -- smolinit.telnetd=23
   smolinit.securetty=/dev/ttyS0".  No serial getty (console is output-only).

REBOOT now works (it did not before):
 - mach_reset was never set for E17, so machine_restart fell through to for(;;)
   - and because the watchdog hard-petter runs from BOTH CPUs' ticks, CPU0
   going quiet was not enough; CPU1 kept petting and the board sat in reboot
   forever (observed: "reboot: Restarting system" then a pinging-but-dead
   board).  Fixed: mach_reset = e17_reset, which parks the secondary (CPU2CON
   SRESET=0, stopping its tick+petting) then spins with IRQs off; the watchdog
   then fires a full SYSRESET -> RMON -> u-boot.  VERIFIED: `reboot` as root
   resets the board to the u-boot prompt.

Net effect: fully self-service now - su to root, reboot to reset, netboot from
u-boot - no hardware reset needed for normal iteration.

Tooling added to the repo (the sandbox wipes /tmp): scripts/e17-conlog.py
(persistent capped console logger -> build/console.log) and
scripts/e17-telnet.py (auth-aware telnet client, --root to su).

Patches refreshed: patches/e17-uboot-uart-watchdog.patch and
patches/e17-linux-uart-watchdog-lockup.patch (kernel side; also needs
CONFIG_TMPFS_XATTR=y).

Still open: robust serial console RX under load (console_rx=0 by default); the
whole-bus cross-call hang under heavy cross-call load (distinct from reboot,
which is now fixed); MAC PROM decode (04:00:04:00:04:00); QEMU model.


==========================================================================================
ADDENDUM 2 - MAC fixed; serial-RX-under-load root-caused to an SMP CPU2CON race
==========================================================================================

MAC: fixed and verified.  The station address is six plain bytes in the NVRAM
board-ID block at 0xfec20488 (00 00 5b 00 49 62), NOT the ILACC/LANCE window at
0xfec69d81 (which just returns a constant 00 00 00 04 -> the bogus
04:00:04:00:04:00).  Both readers (u-boot dummy.c, linux e17-lance.c) now read
the NVRAM.  u-boot banner and Linux eth0 both show 00:00:5b:00:49:62; the
correct MAC gets a stable DHCP lease (192.168.2.154).

SERIAL RX ("uart totally fixed"): output console is rock-solid and never wedges;
console_rx defaults off (telnet is the input path).  Turning console_rx=1 and
driving heavy serial input + concurrent telnet load still wedges the board.
Added a real fix along the way (clamp RFOC to the 16-byte FIFO in rx_chars, it
was unbounded), but it does not eliminate the wedge.

Root cause (breadcrumb): it is not a CD2401 bus fault (region=none, not in the
IACK/RX regions).  CPU0's last-tick PC is arch_cpu_idle+0x30 - the BOUNDED,
register-only spin-idle loop with IRQs enabled - yet its (non-maskable, level-7)
tick then stops, and CPU1 hangs in smp_call_function_many_cond waiting for CPU0.
A register-only spin cannot halt a CPU, so CPU0's tick/IRQ delivery itself was
disrupted.  That points at the documented hazard: cross-CPU CPU2CON access is
unsafe (SIPL/SICF overlap), and CPU1 acks its VIC clock through CPU2CON every
tick while CPU0 also writes CPU2CON for IPI doorbells.  Under load these race
and can knock out CPU0's VIC-clock / IRQ context.  Serial RX just raises the
cross-call rate and exposes it; it is the same underlying bug as the "whole-bus
cross-call hang", NOT a UART bug.

Net: the UART is fixed for reliable use (stable output console + telnet input,
console_rx=0).  Making serial RX robust under load requires serialising /
redesigning cross-CPU CPU2CON access (VIC-clock ack + IPI doorbells) - a deeper
SMP change with deadlock risk in the level-7 tick path, tracked separately.
